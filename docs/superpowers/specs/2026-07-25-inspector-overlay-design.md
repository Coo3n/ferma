# Визуальный инспектор UI: оверлей поверх экрана

Дата: 2026-07-25

## Задача

Сейчас инспектор показывает иерархию UI одним куском сырого XML в `<pre>`
(`static/index.html`, функция `dumpUi`). Чтобы получить селектор для сценария,
приходится глазами искать нужный узел в дампе на сотни строк и вручную
сопоставлять его с тем, что видно на экране.

Нужно: кликнуть по элементу прямо на картинке экрана, увидеть разметку и сразу
получить готовый селектор.

## Поддержка Jetpack Compose

`dump_hierarchy()` (`farm/control.py:251`) идёт через uiautomator2 →
AccessibilityNodeInfo. Compose рендерит всё в один `ComposeView` и отдаёт узлы
через semantics-слой. В дампе доступно:

- `text` — работает
- `content-desc` — работает
- `resource-id` — **пусто**, пока приложение не включит `Modifier.testTag()`
  вместе с `semantics { testTagsAsResourceId = true }`. Это делается на стороне
  приложения, со стороны фермы не чинится
- `class` — почти везде generic `android.view.View`, для селектора бесполезен

Значит для Compose-приложений остаются `text=` и `description=`. Это и есть
главный довод за визуальный инспектор: такие узлы тяжело опознать в XML, но
легко ткнуть пальцем на картинке.

## Решения

| Вопрос | Решение |
|---|---|
| Как развести тап и инспекцию | Тумблер «инспектор» в шапке экрана |
| Синхронизация рамок с картинкой | Кадр замораживается, кнопка «⟳ обновить» |
| Что показывает панель | Селектор + уникальность + альтернативы + атрибуты |
| Некликабельный узел | Автоподъём к clickable-предку с ограничителями |
| Где живёт логика | На сервере, новый модуль `farm/inspect.py` |

### Почему логика на сервере

Рассматривались три варианта: разбор XML на сервере, разбор в браузере через
`DOMParser`, и гибрид. Выбран серверный, по трём причинам:

1. Логика селекторов оказывается рядом с `farm/context.py`, где определён тот
   самый `ctx.click(**selector)`. Один источник правды.
2. Скриншот и иерархия снимаются одним запросом — рамки гарантированно
   относятся к тому же моменту, что картинка. При разборе на клиенте это два
   запроса, между которыми экран успевает смениться.
3. Логика покрывается тестами на сохранённых дампах, без устройства. В браузере
   это не протестировать.

Цена — новый модуль примерно на 150 строк.

## Архитектура

### Компоненты

| Файл | Что делает | Статус |
|---|---|---|
| `farm/inspect.py` | Парсит XML → узлы, строит селекторы, считает уникальность | новый, ~150 строк |
| `farm/server.py` | Эндпоинт `GET /api/devices/{serial}/inspect` | +12 строк |
| `static/inspector.js` | Оверлей, режим, панель селектора | новый, ~180 строк |
| `static/index.html` | Тумблер, контейнер оверлея, подключение скрипта | +30 строк |
| `tests/test_inspect.py` | Тесты логики селекторов на дампах | новый |

`inspect.py` не обращается к adb напрямую — принимает готовый XML и размеры
экрана. Поэтому тестируется на строках.

Инспектор выносится в отдельный `static/inspector.js`, а не дописывается в
`index.html`: тот уже около 1000 строк и содержит стили, разметку и весь JS
разом. Остальной код не трогаем.

### Поток данных

```
[тумблер «инспектор» ON]
        │
        ▼
GET /api/devices/{serial}/inspect
        │
        ├─ control.dump_hierarchy(serial)                          XML
        ├─ control.screenshot(serial, max_width=ARTIFACT_MAX_WIDTH) JPEG
        └─ control.size(serial)                                    (w, h)
        │
        ▼
inspect.parse(xml, w, h) → плоский список узлов
        │  bounds → доли 0..1
        │  для каждого узла: кандидаты-селекторы + число совпадений
        ▼
JSON { width, height, screenshot: "data:image/jpeg;base64,...", nodes: [...] }
        │
        ▼
[фронт] стрим на паузу → показываем этот кадр → рисуем рамки поверх
```

### Формат ответа

```json
{
  "width": 1220,
  "height": 2712,
  "screenshot": "data:image/jpeg;base64,...",
  "nodes": [
    {
      "id": 42,
      "parent": 17,
      "bounds": [0.03, 0.30, 0.55, 0.34],
      "text": "Войти",
      "resourceId": "com.app:id/login_btn",
      "description": "",
      "class": "android.widget.Button",
      "clickable": true,
      "selectors": [
        {"kwarg": "resourceId=\"com.app:id/login_btn\"", "matches": 1},
        {"kwarg": "text=\"Войти\"", "matches": 3}
      ]
    }
  ]
}
```

Скриншот передаётся инлайном в base64. Иначе картинка и рамки — два запроса, и
между ними экран уезжает; ровно этот рассинхрон мы и устраняем заморозкой
кадра. Цена — плюс треть к весу, при `ARTIFACT_MAX_WIDTH=1080` это 200–400 КБ на
снимок. Для локальной фермы несущественно.

`bounds` отдаются долями `0..1`, а не пикселями. Картинка ужимается до 1080 px,
затем `<img>` ещё раз масштабируется под размер панели. Доли переживают оба
масштабирования: `left = bounds[0] * img.clientWidth`. Тот же приём уже
используется в жестах по стриму (функция `norm` в `static/index.html`).

## Алгоритм выбора селектора

### Шаг 1. Клик → узел

Из клика получаем долевые `(x, y)`. Кандидаты — узлы, чьи `bounds` содержат
точку. Побеждает наименьший по площади: самый глубокий видимый элемент под
курсором. Узлы нулевой площади отсеиваются при парсинге — кликнуть по ним
нельзя.

### Шаг 2. Автоподъём к clickable-предку

Важное уточнение: `el.click()` в uiautomator2 вычисляет центр `bounds` и тапает
по координатам, а не вызывает `performAction(CLICK)` на узле. Поэтому
`clickable=false` сам по себе тап не ломает — касание приходит в ту же точку
экрана, и Android отдаёт его обработчику родителя. Именно так работает
существующий `ctx.click()` (`farm/context.py:130`).

Реальная опасность в другом: подъём вслепую уводит центр. У `Column`, обёрнутой
в кликабельный `Row` на всю ширину, центр предка окажется на пустом месте.

Поднимаемся вверх, пока узел `clickable=false`, останавливаясь если:

- пройдено 4 уровня — дальше почти всегда контейнер, а не кнопка;
- площадь предка больше 4× площади ребёнка — центр уже не там, куда кликнули;
- предок занимает весь экран — это корень.

Предок берётся только если даёт селектор лучше, то есть имеет собственный
`resourceId` или `description`. Если идентификаторов у предка нет, а у ребёнка
есть текст — остаётся ребёнок: его центр-тап сработает.

Панель сообщает, что произошло: `выбран clickable-предок (↑2)` либо
`узел не clickable — тап по центру сработает`.

### Шаг 3. Кандидаты-селекторы

| # | Селектор | Обоснование приоритета |
|---|---|---|
| 1 | `resourceId="..."` | Переживает смену языка и правку текстов |
| 2 | `description="..."` | Задан разработчиком явно, стабилен |
| 3 | `text="..."` | Ломается от локализации и динамики, но на Compose часто единственный |
| 4 | `className="...", instance=N` | Крайний случай, хрупко к перевёрстке |
| 5 | `ctx.tap(0.42, 0.31)` | Если идентификаторов нет вовсе |

Пустые и состоящие из пробелов значения в кандидаты не идут. Для Compose пункты
1 и 2 обычно пусты, список закономерно съезжает на `text` — это ожидаемое
поведение, а не сбой.

### Шаг 4. Уникальность

Для каждого кандидата считается, сколько узлов во всём дампе ему удовлетворяют.
Сравнение — точное равенство строки, как в uiautomator2. `matches: 1` даёт
зелёную отметку, `matches: 3` — предупреждение.

Если ни один одиночный кандидат не уникален, добавляется комбинированный
(`text="Войти", className="android.widget.Button"`) и считается так же. Если и
он не помог — `instance=N`, уникальный по определению, но помеченный как
хрупкий.

Лучшим показывается первый уникальный по приоритету. Если уникальных нет —
первый по приоритету, с честной пометкой о числе совпадений.

## Фронтенд

### Разведение режимов

Обработчик жестов висит на `.stage` и на первой строке отсеивает чужие цели:

```js
if(ev.target.id !== 'screen') return;
```

Оверлей ложится поверх `#screen`, поэтому при включённом инспекторе `ev.target`
— оверлей, и тап по устройству не уходит сам собой. При выключении оверлей
скрыт, цель снова `#screen`. Логика жестов не меняется.

### Позиционирование оверлея

`#screen` центрируется во flex-контейнере и ужат `max-width`/`max-height`,
поэтому его прямоугольник меньше `.stage`. Оверлей позиционируется абсолютно
внутри `.stage` (добавляется `position:relative`) и синхронизируется с
`getBoundingClientRect()` картинки по событию `load` и через `ResizeObserver`.

Вариант с обёрткой картинки в `<div>` отвергнут: `startStream()` подменяет узел
`#screen` целиком, и вокруг него завязаны flex-центрирование и «безель» из
четырёх теней.

### Замороженный кадр

`startStream()` — единственное место, владеющее `#screen`. Добавляется ветка:
при включённом инспекторе `img.src` берётся из base64-кадра ответа `/inspect`.
Картинка и рамки происходят из одного снимка.

### Отрисовка рамок

- **Всегда** — тонкий контур на узлах, имеющих `text`, `resourceId` или
  `description`, то есть на тех, куда можно целиться селектором.
- **Под курсором** — яркая подсветка и ярлык с текстом или id. Попадание
  считается в JS по массиву узлов; на 300 узлах поиск незаметен.
- **Выбранный** — держится акцентным цветом до следующего клика.
- **Галка «все узлы»** — показать всё, включая контейнеры без идентификаторов,
  когда нужно понять структуру.

Рисовать все узлы постоянно нельзя: триста рамок превращаются в кашу.

### Панель

В существующую колонку `#pane-insp` сверху добавляется блок «Выбранный
элемент»: строка `ctx.click(...)` с кнопкой копирования, отметка уникальности,
альтернативные селекторы, атрибуты узла. Кнопка «UI-дерево» и `<pre
id="inspOut">` остаются — сырой XML иногда нужен.

В шапку экрана добавляется кнопка «⟳ обновить» для пересъёма.

### Сброс состояния

Инспектор выключается при смене устройства и при обрыве стрима: рамки от одного
экрана поверх другого хуже, чем их отсутствие.

## Обработка ошибок

| Отказ | Поведение |
|---|---|
| `uiautomator2` не подключён | `dump_hierarchy()` падает на `adb shell uiautomator dump` — медленнее, но работает |
| Оба способа не смогли (анимация, «could not get idle state») | 500 → тост с текстом, тумблер откатывается в OFF, стрим не трогаем |
| Скриншот не снялся | То же: снимок атомарный, либо оба, либо ничего |
| Устройство отвалилось | Общий обработчик, как у остальных ручек |
| Битый XML | `ET.ParseError` ловится в `inspect.py`, отдаётся 500 с понятным текстом |
| Узлов ноль | Панель пишет «ничего не распознано» |
| `WebView` / `SurfaceView` / Unity | Узлов не будет — ограничение accessibility. Сообщается прямо в пустом состоянии, чтобы причину не искали в ферме |

У корневого узла `bounds` иногда выходит за пределы экрана — вырезы,
split-screen. Доли зажимаются в `0..1`, иначе рамка уползёт за картинку.

## Тестирование

`tests/test_inspect.py`. `pytest` добавляется в `requirements.txt` — сейчас его
нет, тестов в проекте тоже нет, каталог заводится этим шагом.

Фикстуры — два реальных XML-дампа, снятых кнопкой «UI-дерево»: обычная
View-иерархия и Compose-экран. Устройство тестам не нужно.

Проверяется:

- разбор `bounds`, включая зажим в `0..1`;
- выбор наименьшего узла по точке;
- все три ограничителя подъёма: 4 уровня, 4× площади, корень;
- приоритет кандидатов;
- подсчёт совпадений, включая комбинированный селектор и `instance`;
- отсев пустых и пробельных атрибутов;
- Compose-кейс: пустой `resourceId` корректно съезжает на `text`.

Ручная проверка: рамки совпадают с элементами, скопированная строка реально
срабатывает в сценарии.

## Замечание про права на ввод

Инспектор ничего не инжектит — только `dump_hierarchy` и `screenshot`, оба
read-only. Он работает на устройствах, где `input tap/swipe` отклоняется с
`SecurityException: Injecting input events requires ... INJECT_EVENTS`
(актуально для HyperOS/MIUI без тумблера «USB-отладка (настройки
безопасности)»). Тапы по стриму на таких устройствах не работают, инспекция и
сборка селекторов — работают.

## Вне объёма

- Правка XML-дампа или запись сценария по кликам
- Диффы иерархии между кадрами
- Оверлей поверх живого, не замороженного стрима
- Поддержка `WebView` через включение accessibility в приложении
