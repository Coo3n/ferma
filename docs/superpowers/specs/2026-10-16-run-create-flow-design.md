# Сквозной путь «создал → запустил → разобрался» — дизайн

Дата: 2026-10-16. Подход 1 из брейншторма (сквозной путь), утверждён.

## Цель

Главная работа оператора — создавать сценарии и запускать их на ферме из ~40
телефонов. Сейчас путь рвётся на стыках разделов, запуск устроен четырьмя
разными способами, а причины будущих падений (нет аккаунта, бан) не видны до
прогона. Делаем одну непрерывную дорогу и убираем дубли, которые на ней лежат.

Не цель: менять визуальный стиль (токены `base.css` остаются), трогать
синхронное управление и массовые действия.

## A. Единые компоненты

### A1. Окно запуска — `openRunDialog({scenario, serials})` (новый `static/js/rundialog.js`)

Одна точка запуска сценария на ферме. Заменяет:

| Сейчас | Станет |
|---|---|
| Панель фермы: select сценария + «Повторов» + «Запустить» (`runScenario`) | кнопка «Запустить…» → `openRunDialog({serials: выбранные})` |
| «Сценарии»: «Повторов» + «Запустить» (`scRunBarHtml`, `runScenario`) | кнопка «Запустить…» → `openRunDialog({scenario})` |
| «По группам» (`groupRunMenu`/`groupRunGo`) | режим окна «по группам» — тот же компонент |

Не заменяет панель проверки в конструкторе (`stRunBuild`): там прогон на одном
открытом телефоне с выбором шага и скорости — другая задача.

Содержимое окна:
1. Сценарий (select; предвыбран, если передан) и параметры сценария (тот же
   `paramField`, что сейчас на «Сценариях»).
2. Кто запускает: «Выбранные (N)» / «Группа …» / «Все в сети» — если `serials`
   не переданы, по умолчанию «Все в сети».
3. Повторов.
4. Сводка готовности (см. B) и кнопка «Запустить на K».

После запуска — переход в «Запуски» на этот запуск (см. C2).

### A2. Общие помощники в `core.js`

- `armConfirm(btn, armedText)` → `true`, если это второе нажатие в течение 4 с;
  иначе взводит кнопку (`data-armed`, класс `armed`, текст `armedText`) и
  возвращает `false`. Заменяет три копии: `bulk.js` (перезагрузка, очистка
  данных), `accounts.js` (удаление).
- `store.get(key, fallback)` / `store.set(key, value)` — JSON в localStorage в
  try/catch. Заменяет обёртки в `bulk.js`, `fleet.js`, `core.js`.
- `emptyState({art, title, text, action})` — разметка пустого экрана тем же
  способом, что на ферме/задачах. «Аккаунты» переходят на него.

### A3. Одна система подсветки

| Состояние | Вид | Где обязано работать |
|---|---|---|
| выбрано | зелёная рамка `--accent` | плитки, строки аккаунтов, карточки сценариев |
| идёт работа | фиолетовая точка с пульсом `--busy` | плитки, запуски, бейдж «Запуски» |
| требует внимания | красный бейдж/точка `--bad` + текст | плитки, «Запуски», «Проблемы», аккаунты «бан» |
| предупреждение | жёлтый `--warn` + текст | «нужен вход», батарея, нет аккаунта |
| фокус клавиатуры | `:focus-visible` обводка 2px `--accent` | все кнопки/поля, включая добавленные в этой сессии (`bulk.css`, `.seg`, `.live-switch`, `.phone-pick`, `.gr-try`) |

Цвет никогда не единственный признак: рядом всегда слово или иконка.

## B. Проверка перед запуском

### B1. Какие аккаунты нужны сценарию (сервер)

`farm/scenarios.py`: при загрузке сценария выделять платформы из вызовов
`ctx.account("<p>")` в исходнике (AST, только строковые литералы из
`accounts.PLATFORMS`). Поле `needs_accounts: list[str]` отдаётся в
`/api/scenarios`. Для рецептных сценариев это же видно из шагов
`type.args.account` — источник один: код.

### B2. Готовность телефонов (сервер)

`POST /api/run/preflight {scenario, serials}` → по каждому телефону статус:

| статус | условие | по умолчанию |
|---|---|---|
| `ready` | в сети, свободен, аккаунты есть и не `banned` | запускать |
| `offline` | не в сети | пропустить |
| `busy` | идёт задача | поставится в очередь (так работает сейчас) — показывать |
| `no_account` | нет аккаунта платформы из `needs_accounts` | пропустить |
| `banned` | аккаунт со статусом `banned` | пропустить |
| `login` | аккаунт со статусом `login` | запускать, с предупреждением |

Ответ: `{counts: {ready: 38, no_account: 2, ...}, devices: {serial: {status, platform?}}}`.

### B3. Сводка в окне запуска

Строка: «38 готовы · 2 без аккаунта VK · 1 занят (в очередь)». Под ней —
только проблемные телефоны списком, с действиями:
- «Пропустить» (по умолчанию для offline/no_account/banned);
- «Раздать аккаунты» — вызывает существующий `/api/accounts/autobind` для
  платформы и перезапрашивает preflight.

Кнопка: «Запустить на K». Если K = 0 — кнопка выключена через
`disableWithReason` с причиной.

### B4. Аккаунт на плитке

`/api/devices` получает `accounts: [{platform, status}]` (без логинов и
паролей). Плитка показывает значок у имени: красный при `banned`, жёлтый при
`login`. Отсутствие аккаунта на плитке не показываем (зависит от сценария) —
это делает B3.

## C. Стыки между разделами

### C1. Конструктор → ферма

После успешного сохранения сценария тост с действием «Запустить на ферме» →
`openRunDialog({scenario: key})`.

### C2. Запуск → «Запуски»

`runner.submit` получает `batch` (id запуска, общий для всех задач одного
нажатия) — поле у `Job` и в `to_dict`. После запуска «Запуски» открываются с
фильтром по `batch` и шапкой: «auth на 40: 12 готово · 1 сбой · 27 в работе»
и кнопкой «Показать все запуски» (снять фильтр).

### C3. Сбой → конструктор

В журнале упавшей задачи — кнопка «Починить шаг», та же, что на карточке
«Проблем» (`deviationRepairButton` → вынести в общий `repairButtonHtml(jobOrItem)`),
без второй реализации.

## D. Карточка сценария на «Сценариях»

Под именем: соцсети, которым нужен аккаунт (из `needs_accounts`), и итог
последнего запуска — «вчера · 38 ок · 2 сбоя» (из задач с этим сценарием в
`/api/jobs`, последний `batch`). Кнопка «Запустить…» (A1) и «Изменить»
(уже есть).

## Порядок работ

1. A2 помощники + замена копий (без изменения поведения).
2. B1–B2 сервер + тесты.
3. A1 окно запуска + B3 сводка; удалить старые точки запуска.
4. C2 batch + фильтр; C1; C3.
5. B4 значок аккаунта; D карточка; A3 фокус/подсветка.
6. Один проход в браузере на моках, pytest.

## Тесты

- `needs_accounts`: сценарий с `ctx.account("vk")` и `ctx.account("tg")` →
  `["tg", "vk"]`; без вызовов → `[]`; нелитеральный аргумент игнорируется.
- preflight: офлайн, занят, без аккаунта, бан, «нужен вход», готов.
- `batch`: все задачи одного `submit` несут один id; разные вызовы — разные.
- `codegen`/`steps` — уже покрыто тестами ввода из аккаунта.

## Риски

- Удаление select сценария с панели фермы меняет привычку: компенсируем тем,
  что окно запуска открывается одной кнопкой и помнит последний сценарий
  (`store`).
- Определение аккаунтов по коду не увидит `ctx.account(переменная)` — такой
  сценарий просто не получит проверки (не ложная тревога).
