# Android Farm — подробное руководство

> Короткий обзор, запуск и устройство проекта — в [README](../README.md). Здесь — как работает каждый механизм фермы.

Локальное веб-приложение для macOS: подключаешь телефоны по USB, видишь их
экраны в браузере, управляешь мышью и клавиатурой, записываешь сценарии
кликами и запускаешь их сразу на нескольких устройствах.

Рассчитано на 1–20+ устройств: каждое устройство работает в своём потоке,
трансляция экрана запускается только для того, которое реально смотрят.

## Установка

```bash
brew install --cask android-platform-tools   # adb
brew install scrcpy                          # опционально: плавное окно устройства
cd android-farm
chmod +x run.sh
./run.sh            # сервер (backend/) + сайт (frontend/) одной командой
```

Первый запуск создаст `.venv`, поставит зависимости и откроет
<http://127.0.0.1:8777>.

На телефоне: **Настройки → О телефоне → 7 тапов по «Номер сборки»**, затем
**Для разработчиков → Отладка по USB**. При подключении подтвердить RSA-ключ
(галка «Всегда разрешать с этого компьютера»).

## Как это работает вместе

Ферма построена вокруг одного цикла. Каждый механизм в ней — шаг этого цикла,
а не отдельная фича:

1. **Записали** сценарий кликами по экрану устройства — получился обычный
   `.py`-файл в `backend/scenarios/`.
2. **Запустили** его на двадцати устройствах. Часть прогонов уехала не туда:
   чужой попап, A/B-онбординг, пейволл, переехавшая кнопка.
3. Ферма **сама пытается** выправиться: ждёт дорисовки экрана, даёт ход
   стражам, ищет цель запасными слоями, в крайнем случае выбирается с
   незнакомого экрана перебором кнопок.
4. Не вышло — задача **встаёт и ждёт человека**, не отпуская устройство:
   экран ещё тот, на котором споткнулись.
5. Всё, что пошло не по сценарию, попадает в раздел **«Отклонения»** — одна
   строка на причину, а не на устройство.
6. Из отклонения человек **показывает кликами**, как пройти это место. Из
   показанного рождается **отвод** (ферма обходит сама) или **ветка развилки**
   (сюжет официально расходится). В следующий раз никто никого не ждёт.

Всё остальное в этом README — подробности по каждому шагу.

## Интерфейс

**Сверху — четыре раздела:** «Ферма», «Сценарии», «Задачи» и «Отклонения»
(последний со значком непрочитанных). Горячие клавиши `g`, `s`, `j`, `o`; `d`
возвращает к открытому устройству, `/` — в поиск по ферме.

**«Ферма»** — плитки всех устройств с превью экрана, зарядом и температурой.
Галочка выбирает устройство для запуска сценариев, клик по карточке открывает
его рабочее место. Двойной клик по имени — переименовать (удобно подписать
«Pixel-01», «Samsung-03»). Кнопка «Настроить» отключает анимации и не даёт
экрану гаснуть при зарядке. Фильтр «Тревоги» здесь — про **здоровье
устройств** (перегрев, заряд), это не то же, что раздел «Отклонения».

**Рабочее место устройства** — экран по центру: клик = тап, перетаскивание =
свайп, удержание 0.6 с = долгое нажатие. Поле снизу вводит текст (кириллица
работает через uiautomator2), галка «живая клавиатура» пробрасывает нажатия
физической клавиатуры на телефон. Кнопка **scrcpy** открывает нативное окно с
30–60 fps — для ручной работы оно приятнее, чем поток скриншотов.

Рабочее место — это конструктор сюжета: холст со схемой сценария занимает
всю площадь, зеркало экрана стоит справа узкой колонкой. Границу между ними
тянут мышью (или стрелками с клавиатуры, когда она в фокусе), кнопка
**«Экран»** сворачивает зеркало целиком — развилке на пять веток нужна вся
ширина окна. Ширина и свёрнутость запоминаются.

Холст масштабируется: `Ctrl`/`⌘` + колесо или кнопки `−` / `+`, «вписать»
показывает сюжет целиком, процент возвращает 100%. Панорама — перетаскивание
пустого места холста; за карточку тащат её саму.

Разовые команды устройству живут в диалоге **«Управление»** в шапке: запуск
приложения по пакету, открытие ссылки, Force-stop, `adb shell`, дамп
UI-дерева и logcat. Они нужны раз за сеанс и не занимают места на экране.

## Селекторы шагов

Запись строит селектор шага сама, по дампу иерархии экрана. Приоритет:
`resourceId` → `description` → `text` → связка с `className` → `instance` →
координаты. Кандидат, однозначный на экране, поднимается выше
неоднозначного, а запасные варианты остаются в строке шага — их видно в
«Списке» и можно переключить руками.

Для приложений на Jetpack Compose `resourceId` обычно пуст: нужен
`Modifier.testTag` вместе с `semantics { testTagsAsResourceId = true }` на
стороне приложения. Поэтому селектор строится по `text` или `description` —
это ожидаемое поведение, а не сбой.

Узлов не будет вовсе у `WebView`, `SurfaceView` и игр: они не отдают дерево
через accessibility. Это ограничение Android, а не фермы — шаги там пишутся
координатами.

Дамп иерархии ничего не инжектит, он read-only. Поэтому сборка селекторов
работает и на устройствах, где `input tap/swipe` отклоняется с
`SecurityException: ... INJECT_EVENTS` (HyperOS/MIUI без включённого тумблера
«USB-отладка (настройки безопасности)»): тапы по стриму там не работают, а
запись селекторов — работает.

## Конструктор сценариев

Вкладка «Сценарии» → **«Создать записью»** (уводит к открытому устройству:
шаги пишутся кликами по экрану, а экран есть только там). Кнопка «● Запись»
запоминает всё, что вы делаете с устройством: тапы, свайпы, ввод текста,
клавиши, запуск приложений со вкладки «Управление».

Клик в режиме записи делает три вещи разом: тапает устройство, подсвечивает
найденный элемент рамкой и добавляет шаг с готовым селектором. Метка `✓` у
шага означает, что селектор однозначен, `⚠3` — что под него подходят три
узла: тогда разверните шаг и выберите другой вариант.

Список шагов справа — это и есть ревью. Шаг можно удалить, переставить,
поменять у него значение или селектор, развернуть и увидеть миниатюру момента
с рамкой на цели. Кнопка `{}` выносит значение в `PARAMS` — дальше сценарий
запускается на двадцати устройствах с разными данными.

Шагу клика можно добавить запасные слои резолвера — текст, кроп картинки,
координаты; тогда в код попадает `ctx.click_target(...)` вместо простого
`ctx.click(...)`. Отдельные типы шагов дают **якорь экрана**
(`ctx.expect_screen`) и **развилку** (`ctx.which_screen`) — см.
[«Устойчивость»](#устойчивость). Вырезанные кропы кладутся рядом с файлом
сценария, в `backend/scenarios/<имя>_assets/`.

Шаги **перетаскиваются мышью** за ручку `⠿` слева: взяли, уронили куда надо,
линия показывает, встанет шаг выше или ниже цели. Кнопки ↑↓ остались — с
клавиатуры и на длинном списке они быстрее, чем тащить через весь экран.
Тащить можно только за ручку: внутри строки живут поля ввода и селекты, и
строка, которую хватаешь в любом месте, отняла бы у них выделение текста.

### Проверка и правка на ходу

- **Отмена/возврат** — `Ctrl/⌘+Z`, `Ctrl/⌘+Y` (или кнопки в панели); правки одного поля сливаются в одну запись.
- **Дубль шага** и **выбор группы** (галки в списке, Shift — диапазон): необязательные, повторы, пауза после каждого, дублировать, удалить.
- **Необязательный шаг** и **повторы** (в раскрытом шаге): в код попадает `ctx.attempt(lambda: ..., retries=N, optional=True)`. Пропущенный шаг оставляет кадр и пометку в отчёте.
- **Проверить** (панель записи): валидация (`/api/recorder/validate`: шаги, параметры, блоки развилок, кропы, пакеты на устройстве), запуск целиком или **с шага N** (`▶` в строке), замедление 0.5×/0.25×, живая подсветка шага и прогресс, кнопки «повторить/пропустить» при остановке. Несохранённые правки перед запуском записываются в файл.
- **Изменения** — дифф с последней сохранённой версией; при наведении на шаг жест (свайп, тап) рисуется на экране.
- В журнале задач: цепочка шагов, «таймаут» против «отказа» с подсказкой, `report.json` в артефактах.
- Новые шаблоны в библиотеке: скролл, следующая страница, поиск, авторизация.

### Схема

Схема — вид по умолчанию в панели записи: не отдельная кнопка и не модалка, а
постоянная панель рядом с устройством. Переключается чипами **«Схема»** /
**«Список»** над списком шагов и растёт живьём по мере записи: хребет шагов,
а под развилкой — дорожки ветвей с карточкой блока на каждой:

```
▼ Разблокировать
▌ Запуск com.android.chrome
● Якорь: экран «поиск»
◆ Развилка «после входа»
    онбординг →  [Заглушка: закрыть онбординг]
    каталог   →  ничего не делать
    пейволл   →  блок «udalennyy_blok» не найден
▼ Тап по «Дальше»
```

Это единственное место, где сюжет видно целиком: в списке шагов развилка —
одна строка, и куда расходятся пути, приходится домысливать. Всё кликабельно:
узел открывает шаг в списке, карточка блока — сам блок в конструкторе.
Пропавший блок подсвечен красным и там, и в селекте ветки: на прогоне
`ctx.run` упадёт «блок не найден», и причина будет далеко от этого места.

Под хребтом — уже освоенные отводы и преграды, которые ферма ещё не умеет
обходить. Это список дел, а не картинка.

«Список» — тот же сюжет построчно: там, и только там, шаги удаляются,
переставляются и правятся. «Код» показывает, что сгенерировалось. «Сохранить
сценарий» кладёт файл в `backend/scenarios/`, и он сразу появляется в списке со
значком записи. Записанные сценарии можно удалить прямо из списка; написанные
руками — нельзя.

Там, где не распознаются узлы — `WebView`, `SurfaceView`, игры — шаги пишутся
координатами (`ctx.tap(x, y)`). Это ограничение Android, а не фермы.

### Правка записанного сценария

У записанных сценариев в списке есть кнопка `✎`: она открывает их обратно в
конструкторе — со всеми шагами, параметрами, запасными селекторами и кропами.
Шаги правятся как при записи (удалить, переставить, поменять значение,
вынести в `PARAMS`), дописать новые можно кнопкой «● Запись». «Сохранить
изменения» перезаписывает тот же файл; имя файла при правке не меняется —
смена ключа означала бы «сохранить копию». «Не править» выходит, не тронув
файл.

Работает это через **рецепт**: сгенерированный `.py` обратно в шаги не
разбирается, поэтому конструктор кладёт шаги в том виде, в каком их прислал
браузер, в `backend/scenarios/<имя>_assets/recipe.json`. Кнопка `✎` есть только у
сценариев с рецептом — у написанных руками и у записанных до появления
рецептов её нет, и `editable: false` в `/api/scenarios` говорит об этом прямо,
вместо кнопки, которая ничего не откроет.

Перезапись сносит старые кропы: их имена нумеруются по позиции шага, и после
вставки или удаления шага прежние файлы уже не совпадают со своими шагами.
Поэтому картиночные шаги лучше дописывать на том же устройстве, где сценарий
записывали: масштаб шаблона считается от ширины экрана записи, и она берётся
из рецепта, а не из телефона, на котором правят.

Правка, сделанная в `.py` руками, при перезаписи из конструктора теряется —
файл собирается из рецепта целиком. Если сценарий дорабатывали в редакторе,
правьте его дальше там же.

### Блоки: по кругу, с шансом, пока не найдёшь

Выделите шаги галочками и в строке выделения нажмите **«В блок:»**. Есть
три вида блоков, все три можно вкладывать друг в друга, не глубже 3 уровней:

- **↻ по кругу** — крутить шаги N раз или N минут, со случайной паузой между
  кругами. Галочка «следить» включает сторожа: если вылезло окно или
  приложение закрылось, ферма спросит вас.
- **🎲 с шансом** — выполнять шаги иногда. 15 % — примерно в 15 кругах из 100.
  Пример: в повторе «листать ленту» лайк ставится с шансом 15 %.
- **🔎 пока не найдёшь** — крутить шаги, пока на экране не появится цель
  (текст, id или подпись). Если сразу за блоком идёт клик, его цель
  подставляется кнопкой «Взять из шага N». Нужно ограничить число кругов и
  выбрать, что делать, если цель так и не нашлась: идти дальше, остановить
  запуск или спросить вас.

Шаг, перетащенный внутрь рамки, входит в блок, вытащенный — выходит. Шаг,
записанный внутри рамки, тоже попадает в блок. «Проверить шаг» внутри блока
выполняет его один раз, а проверка заголовка блока прогоняет его содержимое
тоже один раз. «Убрать рамку» оставляет шаги на месте.

### Как искать элемент: «или так»

У клика есть **основной способ** найти элемент и **запасные** («или так»,
до трёх). Шаг нажмёт первое, что найдёт: например, по id `like_button` или по
тексту «Нравится». Свой вариант можно дописать руками, если на другой
прошивке у кнопки другой текст.

**Проверки экрана** ставятся только по желанию: кнопкой «Проверка экрана»
или галочкой «авто-проверки» (по умолчанию выключена). Экраны приложений
меняются, и проверка на каждом шаге роняет рабочий сценарий.

Формат сценария для ИИ-помощника описан в [recipe-format.md](recipe-format.md).

### Развилки в конструкторе

Кнопка **«Развилка»** ставит шаг ветвления. Первая ветка описывает экран,
который сейчас на устройстве; остальные добавляются так же — перейдите на
телефоне к нужному экрану и нажмите «+ ветка с текущего экрана». Каждой ветке
выбирается блок из списка сценариев (или «— ничего не делать —»), и из этого
собирается `ctx.which_screen(...)` с `ctx.run(...)` по ветвям.

Список шагов при этом остаётся плоским: развилка — **один** шаг, а ветвление
живёт в блоках. Блок — обычный записанный сценарий, поэтому ветки
переиспользуются и правятся отдельно, кнопкой `✎`.

Ветвей в одной развилке не больше пяти: дальше это не сюжет, а таблица
переходов, и её место в отдельных сценариях.

## Свои сценарии

Сценарий — обычный `.py`-файл в папке `backend/scenarios/` с функцией `run(ctx)`.
Файлы перечитываются на лету, перезапуск сервера не нужен. Файлы, чьё имя
начинается с `_`, пропускаются — это шаблоны и заготовки.

```python
NAME = "Мой сценарий"
DESCRIPTION = "Что он делает"
PARAMS = {
    "package": {"label": "Пакет", "default": "com.android.chrome"},
    "query":   {"label": "Запрос", "default": "погода"},
}

def run(ctx):
    ctx.watch_popups()                     # сам закроет «Разрешить»
    ctx.unlock()
    ctx.launch_app(ctx.params["package"])
    ctx.click(resourceId="com.android.chrome:id/search_box_text")
    ctx.type(ctx.params["query"])
    ctx.key("enter")
    ctx.sleep(2)
    ctx.screenshot("results")
```

При падении сценария ферма сама сохраняет скриншот, XML UI-дерева, хвост
logcat и слепок преграды в `artifacts/<id задачи>/` — они появляются ссылками
под журналом.

### Что умеет `ctx`

Полный список с примерами — в `backend/scenarios/_template.py`. Если обёрток не
хватает, `ctx.d` — сырой клиент
[uiautomator2](https://github.com/openatx/uiautomator2).

| Группа | Методы |
|---|---|
| Ввод | `tap` `long_tap` `swipe` `scroll_down` `scroll_up` `type` `key` `back` `home` `unlock` |
| Поиск и клик | `click` `click_any` `click_if_exists` `find` `exists` `wait_gone` `set_text` `text_on_screen` |
| Устойчивость | `click_target` `expect_screen` `which_screen` `watch_popups` `escape` `retry` |
| Приложения | `launch_app` `stop_app` `current_app` `wait_app` `open_url` `install` `uninstall` `grant` `packages` |
| Артефакты | `screenshot` `dump_hierarchy` `save_hierarchy` `save_logcat` |
| Прочее | `run` (блок) `log` `sleep` `pause` `fail` `humanize` `shell` `params` `serial` `device_name` `size` `d` |

**Блоки.** `ctx.run("login")` выполняет другой сценарий как часть текущего:
пролог «разблокировать → запустить → войти» пишется один раз. Состояние
прогона общее — человечный режим, стражи и их счётчики не начинают жизнь
заново. Защита от рекурсии и потолок вложенности (5) встроены: блок, который
зовёт сам себя, падает с внятным сообщением, а не вешает устройство.

**Человечный режим.** `ctx.humanize()` на весь сценарий включает разброс
точек тапа, кривые свайпы, посимвольную печать и микропаузы перед
действиями. Конструктор ставит его по умолчанию.

## Устойчивость

Сценарий на реальной ферме редко идёт по идеальному пути: экран не успел
дорисоваться, поверх вылез системный диалог, после обновления приложения
разметка сдвинулась, а половине аккаунтов показали онбординг. Ниже —
механизмы, каждый закрывает свою причину промаха и не дублирует соседние.
Порядок — от самого дешёвого к самому дорогому.

**Ожидание стабильности экрана.** Перед поиском цели (`click`, `click_any`,
`click_target`, `type`, `set_text`) ферма ждёт два одинаковых дампа UI-дерева
подряд — признак, что анимация закончилась. Это best-effort, а не гейт:
вечная анимация (лоадер, видео) не даст дождаться двух одинаковых дампов, и
ожидание просто выходит по таймауту, шаг идёт дальше как есть. Выключается на
сценарий флагом `ctx.settle = False`, глобально — `FARM_SETTLE=0`.

**Стражи.** Известные перехватчики — системные диалоги разрешений, ANR,
предложения оценить приложение — описаны декларативно в `guards/global.json`
(действуют всегда) и `guards/<package>.json` (только когда этот пакет на
экране). Формат — список объектов:

```json
{"name": "permission-allow-ru",
 "when": {"any": [{"text": "Разрешить"}, {"text": "РАЗРЕШИТЬ"}]},
 "action": {"click": {"text": "Разрешить"}},
 "max_fires": 5}
```

`when.any` — список u2-селекторов, страж срабатывает по первому совпавшему;
`action` — ровно одно из трёх:

| Действие | Значение |
|---|---|
| `{"click": {селектор}}` | нажать элемент |
| `{"key": "back"}` | нажать клавишу |
| `{"run": "ключ_сценария"}` | выполнить блок — так работают [отводы](#отводы-обучение-на-месте) |

`max_fires` (по умолчанию 3) — потолок срабатываний одного стража за прогон,
чтобы страж, который не помогает, не зациклил задачу. Счётчик считает
**попытки**, а не успехи: иначе страж с битым действием никогда не исчерпал бы
потолок и проверялся бы на каждом промахе.

Стражи не опрашивают экран постоянно в фоне — они пробуются один раз, когда
шаг (`click`, `click_any`, `click_target`, `set_text`, `expect_screen`,
`which_screen`) уже промахнулся, и если хоть один сработал, шаг получает ещё
одну попытку. Файлы читаются заново по времени изменения, перезапуск фермы не
нужен; битый файл или битый страж пропускаются с предупреждением в лог, а не
роняют ферму. Папка задаётся `FARM_GUARDS_DIR`.

**Многослойный резолвер цели.** `ctx.click_target(...)` ищет цель по очереди:
селекторы uiautomator2 (`sel`) → текст по UI-дереву (`text`) → OCR по
скриншоту → поиск кропа по картинке (`img`, ассет из записи конструктором) →
голые координаты (`at`, доля экрана 0..1). Любой аргумент можно опустить —
резолвер пропустит соответствующий слой.

Селекторы и текст пробуются в цикле до таймаута (экран мог ещё
дорисовываться), а слои зрения (OCR, шаблон) — по одному разу за вызов: это
дорогие операции, и повторный снимок того же экрана не даст ничего нового.
Если цель нашлась **не** селектором, в лог попадает предупреждение и
пишется [отклонение](#отклонения-от-сценария) «селектор устарел»: сценарий
доехал, но запас прочности израсходован, и без этого сигнала о поломке узнали
бы только когда отвалится последний слой.

```python
ctx.click_target(sel=[dict(resourceId="com.app:id/login")],
                 text=["Войти", "Log in"], at=(0.5, 0.8))
```

**Якоря экранов.** `ctx.expect_screen(name, any=[...])` проверяет, что
сценарий действительно на ожидаемом экране, прежде чем по нему тапать. Если
ни один из признаков `any` не появился за таймаут, сценарий падает с
понятным сообщением вида «ожидал экран «login», вижу com.other.app: [Вход,
Забыли пароль?]» — вместо тапов в пустоту на чужом экране. В артефакты
падения кладётся текущий скриншот и, если конструктор сохранил эталон
(`expect_<name>.png` в папке ассетов), эталонный кадр рядом: расхождение
видно глазами, а не по XML.

```python
ctx.expect_screen("login", any=[dict(text="Вход")])
```

**Развилки.** `ctx.which_screen({...})` отвечает на вопрос «где я?» и не
падает никогда. Якорь — это «я обязан быть тут», а на живой ферме один и тот
же шаг встречает то онбординг, то пейволл, то сразу каталог, и это норма, а
не сбой:

```python
ветка = ctx.which_screen({
    "онбординг": [dict(resourceId="com.app:id/skip")],
    "каталог": [dict(text="Каталог")],
}, timeout=10)
if ветка == "онбординг":
    ctx.run("skip_onboarding")
```

Порядок вариантов значим: побеждает первый совпавший, поэтому узкие ветки
объявляют раньше широких. Внутри ветки признаки — «любой из», как в
`expect_screen(any=...)`. Действие на ветке — блок, то есть обычный сценарий:
тот же `ctx.run`, что у отводов, с его защитой от рекурсии. Ветка без блока —
это тоже ветка: «экран знаком, делать на нём нечего».

Если не совпала ни одна, сценарий **идёт дальше** (возвращается `default`, по
умолчанию пустая строка) и пишется отклонение «незнакомая ветка»: у сюжета
появился экран, которого никто не описал, а по журналу задач этого не видно
вовсе — прогон-то доехал. Когда «никакая» и есть штатный случай
(необязательный пейволл, которого обычно нет), передают `report=False` —
иначе отклонение писал бы каждый нормальный прогон.

Цена — время: каждый круг проверки стоит примерно полсекунды на признак, и
пока ни одна ветка не совпала, круги идут до `timeout`. Развилка с
`timeout=30` на двадцати устройствах дорога; описать все ожидаемые экраны
ветками дешевле, чем ждать.

**Общий выход с незнакомого экрана.** Если якорь не совпал и стражи
промолчали, ферма пробует выбраться вслепую: `назад` → «закрыть / не сейчас»
→ «пропустить / отмена» → крестик по описанию, два круга с короткими
таймаутами. Это последняя попытка перед падением прогона, и она сознательно
грубая: объявить каждую преграду заранее нельзя, их подсовывает чужое
приложение.

Выключается `FARM_ESCAPE=0` — там, где чужие нажатия недопустимы (оплата,
отправка), лучше упасть, чем угадывать: `назад` не идемпотентен, на коротком
стеке два нажатия выводят из приложения, а «Отмена» на платёжном диалоге
отменяет платёж, а не диалог.

Удачный выход не проходит бесследно: **перед первым нажатием** снимается
слепок экрана (`obstacle_escaped_NN.json` в артефактах задачи) и пишется
отклонение. Иначе такая преграда не видна вообще — прогон доезжает, в журнале
задач всё зелено, а ферма каждый раз заново тыкает кнопки наугад. Если
выбраться не удалось, слепок не пишется: тот же экран снимет падение задачи, и
два слепка одного экрана только раздували бы карту отводов.

### Остановка на человеке (HELD)

Шаг промахнулся мимо цели — вместо падения задача **встаёт и ждёт решения, не
отпуская устройство**. Это главное: отпущенное устройство тут же забирает
следующая задача из очереди и меняет экран, и к тому моменту, когда человек
дойдёт до телефона, показывать уже нечего. Поэтому останавливает не интерфейс
«потом», а сам шаг — здесь и сейчас, на том экране, где споткнулся.

Статус задачи — `HELD`. Он разновидность `running`, а не итог: такую задачу
можно отменить, но нельзя удалить из журнала. В строке состояния она видна
отдельным жёлтым «ждёт N» — это простой телефона, а не работа.

Решение принимается из раздела «Отклонения» или из журнала задачи:

| Решение | Что делает |
|---|---|
| **повторить шаг** | человек поправил экран руками — шаг пробуется заново, с начала своей логики (ожидание, прокрутка, стражи) |
| **пропустить шаг** | шаг не критичный, сценарий идёт дальше без него |
| **уронить задачу** | обычное падение со всеми артефактами, как без остановки |

Кнопка «открыть устройство» рядом — за тем самым экраном. Типовой путь:
открыть, закрыть неожиданный диалог руками, нажать «повторить шаг». Если эта
преграда будет попадаться и дальше, её стоит
[научить обходить](#отводы-обучение-на-месте) — тогда в следующий раз никто
никого не ждёт.

Останавливаются шаги, которые ищут цель: `click`, `click_any`,
`click_target`, `set_text`, `expect_screen`. `which_screen` не
останавливается никогда — он по определению не падает.

**Цена — простой устройства, поэтому потолки жёсткие:**

| Переменная | По умолчанию | Что ограничивает |
|---|---|---|
| `FARM_HOLD` | 1 | `0` — никогда не останавливаться, шаги падают сразу |
| `FARM_HOLD_MAX` | 3 | сколько устройств могут ждать разом: остальные падают как обычно, иначе ночной прогон встал бы весь |
| `FARM_HOLD_TIMEOUT` | 600 | сек ждать человека; не пришёл — задача падает сама |
| `FARM_HOLD_MAX_PER_JOB` | 5 | остановок на одну задачу: «повторить → снова промах» не может длиться вечно |

**Сторож долгих циклов.** Листание ленты не промахивается никогда, поэтому
вылезшее окно или выкинутое приложение раньше листалось до конца сеанса.
Долгий цикл в своём сценарии зовёт `ctx.on_track(package)` после каждого
действия: раз в 20 с ферма
смотрит, своё ли приложение впереди и меняется ли экран. Сбились — сначала
стражи и отводы, потом остановка с вопросом. Главная кнопка — **«Показать, как
быть»**: вы кликами проходите экран на телефоне, ферма сохраняет это как отвод
и сама продолжает запуск; дальше на всех телефонах — без вопросов.
`FARM_WATCH=0` выключает, `FARM_WATCH_EVERY` — интервал, `FARM_WATCH_SAME` —
сколько одинаковых экранов подряд считать застывшим (3).

Сценарий, запущенный не из очереди (из теста, из своего кода), спрашивать
некого — там шаги падают как раньше. Это же верно при `FARM_HOLD=0` и после
исчерпания потолка: остановка добавляет поведение, а не меняет старое.

## Отклонения от сценария

Раздел **«Отклонения»** (горячая клавиша `o`, значок с числом непрочитанных в
навигации) отвечает на вопрос, которого не знает журнал задач: где ферма
пошла не по сценарию и что с этим делать. Это не то же, что фильтр «Тревоги»
на ферме — тот про здоровье устройств (перегрев, заряд). Пять видов:

| Вид | Когда | Что значит |
|---|---|---|
| `падение` | сценарий остановился | прогон встал, дальше без человека никак |
| `ждёт` | задача встала на шаге и держит устройство | нужно решение: повторить, пропустить или уронить |
| `вслепую` | незнакомый экран обошли перебором кнопок | доехало, но что это был за экран — неизвестно |
| `ветка` | развилка не узнала экран | у сюжета появилась ветка, которой никто не описал |
| `селектор` | цель нашлась запасным слоем резолвера | доехало, но селектор устарел и запас прочности израсходован |

Одинаковые отклонения сливаются в **одну строку со счётчиком**: двадцать
устройств об одну стену чинятся одним отводом, а двадцать строк только
спрячут остальное. Слияние идёт только с непрочитанными — «прочитано»
означает «видел и разобрался», и если то же случилось снова, это новость, а
не прибавка к счётчику закрытой строки.

Строки `ждёт` не сливаются между задачами: решение нужно каждой своё, и слить
две стоящие задачи в одну строку значило бы потерять одну вместе с
устройством.

Из строки можно уйти к задаче, к сценарию, открыть устройство или сразу
**научить обходить**. Журнал живёт в памяти, как журнал задач: отклонение без
работающей фермы смысла не имеет, а после перезапуска первый же прогон
запишет его заново. Потолок — `FARM_DEVIATION_HISTORY` строк.

## Отводы: обучение на месте

Отвод — это «ферма умеет обходить эту преграду сама». Рождается он из показа:
нажали «научить обходить» → конструктор открылся в режиме обучения со слепком
той преграды → вы показали кликами, как выйти → «Сохранить отвод».

Сохранение создаёт разом две вещи:

- **блок** в `backend/scenarios/` — обычный записанный сценарий с вашими шагами;
- **стража** в `guards/<пакет>.json` с `action.run` на этот блок и условием
  «как узнать преграду», которое вы выбрали из кандидатов.

Условие снимается **в момент падения**, а не когда человек открыл журнал: к
тому времени устройство уже заберёт следующая задача и экран сменится.
Поэтому «как узнать эту преграду» фиксируется сразу, а «что с ней делать»
человек показывает когда угодно и хоть на другом устройстве.

Кандидаты в условие отбираются осмысленно: узлы чужих приложений (шторка,
навбар, часы) выбрасываются — условие по ним было бы истинным на каждом
экране; `resourceId` идёт первым, потому что не зависит от локали;
узлы размером почти во весь экран уходят в хвост, потому что это каркас
приложения, а не признак экрана.

Карта отводов (`GET /api/detours`, вид «Схема» в конструкторе) показывает
и то, что уже освоено, и **непокрытые преграды** — те, что ферма видела в
бою, но обходить не умеет. Для каждой видно, сколько раз она роняла прогон и
сколько раз её обошли вслепую: второе по журналу задач не видно вовсе.

Отвод против развилки: отвод — про **помеху** (её надо убрать и вернуться на
свой путь), развилка — про **сюжет** (путей несколько, и все законные).

| `FARM_TEMP_ALERT_C` | 42 | порог предупреждения о перегреве |
| `FARM_BATTERY_LOW` | 20 | нижний порог заряда |
| `FARM_BATTERY_HIGH` | 95 | верхний порог заряда |
| **Платы по сети** | | |
| `FARM_NETWORK_DEVICES` | — | адреса через запятую: `10.0.0.5,10.0.0.6:5555` |
| `FARM_NETWORK_FILE` | data/network.json | где хранится список адресов |
| `FARM_NETWORK_PORT` | 5555 | порт по умолчанию, если в адресе он не указан |
| `FARM_NETWORK_TICK` | 5 | как часто сторож проверяет платы |
| `FARM_NETWORK_CONNECT_TIMEOUT` | 10 | потолок одного `adb connect` |
| `FARM_NETWORK_RETRY_BASE` | 5 | начальная пауза перед повтором |
| `FARM_NETWORK_RETRY_MAX` | 120 | потолок паузы между попытками |
| `FARM_NETWORK_WORKERS` | 8 | сколько `connect` идёт разом |

```bash
FARM_PORT=9000 FARM_STREAM_FPS=10 ./run.sh
```

Слои зрения резолвера (OCR и поиск по картинке) требуют отдельных
зависимостей, которые в базовую установку не входят:

```bash
pip install -r backend/requirements-vision.txt
```

Без них ферма работает как обычно — просто эти два слоя молча выключены, цель
ищется селекторами, текстом по дереву и координатами. На macOS OCR идёт через
`ocrmac` (Apple Vision, без скачивания моделей), на остальных платформах —
через `pytesseract` (нужен бинарь `tesseract`). Поиск по картинке — через
`opencv-python-headless` и `numpy`.

## Платы по сети (adb over TCP)

Телефон на проводе adb находит сам. Плата в стойке подключена по Ethernet —
её адрес знает только ферма, и после каждого обрыва подключение надо
восстанавливать. Этим занят **сторож** (`backend/farm/devices/network.py`): раз в
`FARM_NETWORK_TICK` секунд он сверяет список адресов с `adb devices` и
переподключает отставших. Мёртвый адрес не долбится каждые пять секунд —
пауза растёт вдвое (5 → 10 → 20 → 40 с) до `FARM_NETWORK_RETRY_MAX`.

Список адресов живёт в `network.json` рядом с `devices.json` и переживает
перезапуск. Устройства из списка видны в ферме всегда, даже если ни разу не
подключались: из двадцати плиток сразу понятно, какие платы лежат.

### Подготовка платы

```bash
# один раз, пока плата на проводе или с монитором:
adb shell setprop service.adb.tcp.port 5555      # или persist.adb.tcp.port в build.prop
adb push ~/.android/adbkey.pub /data/misc/adb/adb_keys   # чтобы не спрашивала авторизацию
```

Без монитора экран может оказаться чёрным — тогда нужен виртуальный дисплей
(`settings put global overlay_display_devices 1080x1920/320`) или
HDMI-заглушка.

Кнопка «починить» у сетевого устройства делает `disconnect` + `connect` по
адресу, а не перезапускает adb-сервер: перезапуск уронил бы всю остальную
ферму. У устройства на проводе она делает `adb reconnect offline`, а при
неудаче перезапускает сервер.

## API

Интерфейс — тонкий клиент над этим REST. Всё, что делает кнопка, можно
сделать `curl`.

**Устройства и ферма**

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/api/status` | adb, устройства, статистика задач, непрочитанные отклонения |
| `GET` | `/api/devices` · `/api/devices/{serial}` | список и одно устройство |
| `POST` | `/api/devices/{serial}/action` | тап, свайп, ввод, клавиша |
| `POST` | `/api/devices/{serial}/label` · `/enabled` | переименовать, вывести из ротации |
| `POST` | `/api/devices/{serial}/prepare` · `/recover` · `/scrcpy` | подготовить, починить, открыть окно |
| `GET` | `/api/devices/{serial}/stream` · `/frame` · `/thumb` | MJPEG, один кадр, превью |
| `GET` | `/api/devices/{serial}/inspect` · `/hierarchy` · `/logcat` | узлы с селекторами, XML, логи |
| `GET` | `/api/devices/{serial}/packages` | сторонние пакеты |
| `POST` | `/api/adb/restart` | перезапуск adb-сервера и переподключение плат |

**Сценарии и задачи**

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/api/scenarios` | список; `editable` говорит, открывается ли правка |

| `DELETE` | `/api/scenarios/{key}` | удалить (только записанные конструктором) |

| `GET` | `/api/jobs/{id}/artifacts/{name}` · `/obstacle` | артефакты и слепок преграды |
| `DELETE` | `/api/jobs/{id}` · `POST /api/jobs/clear` | вычистить журнал |

| Метод | Путь | Что делает |
|---|---|---|

| Метод | Путь | Что делает |

## Что дальше, при росте до 20 устройств

Приложение готово к 20 устройствам логически, узкими местами станет железо:

- **Powered USB-хабы** с поддержкой `uhubctl` — тогда зависшее устройство
  можно перезагружать по питанию порта, а не руками.
- **Короткие качественные data-кабели** — причина №1 «плавающих» отвалов.
- **Выделенный Mac mini или Linux-мини-ПК** вместо ноутбука,
  `sudo pmset -a sleep 0`, чтобы хост не засыпал.
- **Заряд 20–80%** вместо вечных 100% — иначе батареи вздуваются.

## Red-team стенд (детект vs обход)

Отдельный игрушечный контур для проверки антифрод-логики вашего собственного
приложения: `backend/farm/redteam/detector.py` — наивный risk-scoring детектор фермы
(тайминги, координатная точность повторов, adb-флаги окружения, паттерн
заряда, аптайм), `backend/farm/redteam/harness.py` — гоняет один и тот же сценарий в
двух профилях, «bot» (как есть) и «human» (с добавленной вариативностью
задержек и координат), и считает false negative rate — долю ботовских
прогонов, которые детектор принял за человека.

Это стенд для вашего же детектора, а не тулкит обхода боевых антифрод-систем
реальных платформ (там сигналы совсем другого уровня — аппаратная
аттестация, серверные ML-модели, сетевая репутация). Подробности и запуск — в
`backend/farm/redteam/README.md`.

```bash
cd backend && python -m farm.redteam.harness --all --repeats 5
```

## Структура

Модули, которые не знают ни про adb, ни про FastAPI, помечены «без adb»: на
входе у них словари и строки, на выходе они же, и поэтому они покрыты тестами
без телефона. Это условие тестируемости, а не случайность — см.
`docs/GOTCHAS.md`.
