## Высокий приоритет (P1)

### A01. Отмена последнего шага превращается в успех и запускает остальные телефоны

- Код: `backend/farm/devices/runner.py:710–720`, `899–911`.
- Воспроизведение: начать пробу на A для группы A/B/C; принять отмену во время
  последней операции; операция возвращается без следующей проверки отмены.
- Факт: флаг отмены установлен, но статус становится `passed`, проба — `started`,
  в очереди появляются B и C. Ожидалось завершение с `cancelled` без продолжения.
- Причина: после возврата сценария безусловно присваивается `PASSED`.
- Исправление: согласовать финализацию с отменой; успешный исход нельзя публиковать
  после принятой отмены. Проверять это и перед продолжением пробного запуска.

### A02. Аварийная остановка пропускает ещё не поставленное продолжение пробы

- Код: `backend/farm/devices/runner.py:899–925`, `1016–1022`;
  `backend/farm/api/jobs.py:27–37`.
- Воспроизведение: приостановить поток между выбором успешного исхода пробы
  и постановкой B; вызвать `cancel_all`; возобновить поток.
- Факт: остановка возвращает `ok: true, cancelled: 0`, затем B становится активным.
  Подтверждено и с `everything=False`, и с **`everything=True`**.
- Причина: отменяются только уже существующие задачи; план продолжения пробы
  не аннулируется, постановка происходит вне общей критической секции остановки.
- Исправление: отменять планы продолжения и синхронизировать их постановку
  с остановкой. Одной проверки флага до постановки недостаточно для устранения гонки.

### A03. Ошибка записи аккаунтов скрывается за успешным ответом API

- Код: `backend/farm/accounts.py:69–88`, `112–121`.
- Воспроизведение: создать `old`; на следующем сохранении подставить ошибку
  `os.replace`; через API создать `new`; сбросить кэш, имитируя перезапуск.
- Факт: API возвращает ID; в памяти `old, new`, после перезагрузки только `old`.
- Причина: `_save` проглатывает исключение, изменения памяти не откатываются.
  Та же схема используется изменением и удалением аккаунтов.
- Исправление: возвращать ошибку записи вызывающему коду и сохранять согласованность
  памяти с диском; успех сообщать только после успешной публикации файла.

### A04. Сохранение аккаунтов зависит от отсутствующего на Windows `os.fchmod`

- Код: `backend/farm/accounts.py:75–84`.
- Воспроизведение: моделировать отсутствие `os.fchmod`, вызвать создание аккаунта.
- Факт: API возвращает ID, но `accounts.json` не создаётся.
- Причина: Unix-only API вызывается без проверки платформы; `AttributeError`
  скрывается обработчиком ошибки сохранения (A03).
- Исправление: платформенно корректная установка прав плюс явная обработка
  неудачного сохранения. Исправление только A03 покажет ошибку, но не восстановит запись.
- Уровень доказательства: воспроизведено отсутствие API на macOS; настоящая
  Windows-среда в этом аудите не запускалась.

### A07. Фоновый планировщик затирает восстановленное расписание

- Код: `backend/farm/backup.py:155–174`;
  `backend/farm/schedule.py:330–396`.
- Воспроизведение: загрузить живой Scheduler со сменой `OLD`; восстановить архив
  с пустым расписанием; выполнить обычный tick после конца окна старой смены.
- Факт: сразу после восстановления файл пуст, после tick в нём снова `OLD`.
- Причина: восстановление обновляет файл, но не память работающего Scheduler;
  tick сохраняет прежние данные поверх восстановленных.
- API возвращает `restart_needed: true`, однако до перезапуска фоновая запись
  остаётся разрешённой и может уничтожить результат восстановления.
- Исправление: согласовать восстановление с остановкой/перезагрузкой планировщика
  под блокировками; исключить запись старого состояния в переходном промежутке.

## Средний приоритет (P2)

### A05. Автопривязка назначает несколько аккаунтов одному телефону

- Код: `backend/farm/accounts.py:239–257`.
- Два свободных аккаунта и запрос `serials=["PHONE", "PHONE"]` дают `count: 2`
  и две привязки вместо одной. Подтверждено через обработчик API.
- Причина: множество `taken` не пополняется после назначения.
- Исправление: исключить повторные serials и обновлять занятые телефоны в цикле.
- Условие: дубли в API-запросе; возникновение таких дублей из штатного UI не доказано.

### A06. Одновременный импорт создаёт дубли одного аккаунта

- Код: `backend/farm/accounts.py:214–235`.
- Два конкурентных импорта `same:pw` после одновременного чтения снимка `known`
  создают по одной записи; итоговые логины: `same, same`.
- Причина: проверка уникальности отделена от вставки снятием блокировки.
- Исправление: атомарная проверка уникальности и вставка по паре платформа/логин.
  Иначе дубликаты могут затем выдаваться разным телефонам как разные аккаунты.

### A08. Массовое действие остаётся исполнимым после ответа об ошибке тайм-аута

- Код: `backend/farm/api/bulk.py:191–205`; выполнение очереди: `136–150`.
- Для ещё не запущенного Future дождаться истечения срока `_wait_queued`.
  Ответ: `ok: false, reason: timeout`; последующий `set_running_or_notify_cancel()`
  всё равно возвращает `true`.
- Причина: срок ожидания ответа заканчивается, но отложенное действие не отменяется.
  Пользователь может повторить команду после ошибки и получить два выполнения.
- Исправление: отменять ещё ожидающие действия; для уже выполняющихся отдельно
  показывать неопределённый исход, не выдавая тайм-аут за подтверждённое невыполнение.
- Доказано сохранение исполнимости очереди; физическое действие на телефоне не запускалось.

### A09. При сохранении изменяется пароль с пробелами по краям

- Код: `backend/farm/accounts.py:91–92`.
- Пароль `"  pass word  "` сохраняется как `"pass word"` (13 → 9 символов).
- Причина: общая нормализация `.strip()` применяется также к секрету.
- Исправление: хранить введённый пароль точно; отдельно проверить импорт, где
  `parse_lines` тоже обрезает поля (`181–198`).
