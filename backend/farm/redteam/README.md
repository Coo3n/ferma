# Red-team стенд для антифрод-детектора

Учебный контур: `RiskDetector` (скоринг устройства по одиннадцати сигналам)
и `harness`, который гоняет один и тот же сценарий на ферме в двух профилях
и меряет, ловит ли детектор разницу.

**Что это не такое.** Это не тулкит обхода боевых антифрод-систем реальных
платформ (TikTok, маркетплейсов и т.п.). Аппаратная аттестация и
аккаунт-граф здесь — честные заглушки с точкой подключения, а не имитация:
без вашего бэкенда взять их неоткуда, и стенд в этом прямо признаётся (см.
таблицу ниже). Используйте только против своего же `RiskDetector` на своих
тестовых устройствах.

## Профили

- **bot** — сценарий выполняется как есть: фиксированные паузы (`ctx.sleep`)
  и координаты «пиксель в пиксель» при каждом повторе.
- **human** — та же логика через `RecordingContext(humanize=True)`: перед
  каждым тапом/свайпом случайная пауза 0.15–0.6 с, координаты смещены на
  ±4px, длительность свайпов/долгих нажатий слегка колеблется.

## Сигналы детектора

| Сигнал | Вес | Источник | Что смотрит |
|---|---|---|---|
| `device_attestation` | 30 | **заглушка** — передаёте сами | вердикт Google Play Integrity (`MEETS_DEVICE_INTEGRITY` и т.п.); без адб не получить, должен прийти из вашего приложения на бэкенд |
| `sensor_profile` | 15 | adb, `dumpsys sensorservice` | есть ли акселерометр/гироскоп/магнитометр — на платах без корпуса их иногда физически нет |
| `gesture_trace` | 15 | adb, `getevent -lt` | увидело ли ядро raw touch-события во время жеста (см. ниже, почему это сильный сигнал) |
| `account_graph` | 15 | **заглушка** — передаёте сами | аккаунтов с одного устройства, действий в минуту — берётся из бэкенда вашего приложения |
| `network_subnet` | 12 | adb/`network.json` | сколько других устройств фермы делят с этим одну подсеть /24 |
| `timing_regularity` | 10 | таймстемпы харнесса | разброс интервалов между действиями от прогона к прогону |
| `coord_precision` | 10 | координаты харнесса | разброс пиксельных координат одного и того же действия между прогонами |
| `env_flags` | 10 | adb, getprop/settings | `ro.debuggable`, `ro.secure`, build tags, `su` в PATH, `adb_enabled` |
| `fleet_fingerprint` | 8 | adb, getprop | сколько устройств фермы делят точно такую же `ro.build.fingerprint` (клонированный образ) |
| `power_pattern` | 5 | adb, `dumpsys battery` | заряд ≥95% и на зарядке — типично для стойки, не для телефона в руке |
| `fleet_uptime` | 5 | adb, `/proc/uptime` | аптайм больше ~2 недель — устройство никогда не перезагружают и не носят |

Веса и пороги (`RiskDetector(threshold=...)`) — стартовая точка, не
результат исследования: подбирайте под свои реальные данные через
`detector.register(...)`.

### Почему `gesture_trace` — сильный сигнал

И `adb shell input tap/swipe`, и клики `uiautomator2` кладут событие сразу
во входную очередь `InputDispatcher` (через `InputManager.injectInputEvent` /
`Instrumentation.sendPointerSync`) — в обход `EventHub`, который читает
`/dev/input/eventX`. Поэтому программный тап в норме не оставляет ни одного
сырого kernel-события, а настоящий палец — оставляет всегда. Подделать это
нельзя точечно: пришлось бы менять весь механизм ввода на инжект уровня
ядра (uinput), а не подкручивать параметр. Работает не на всех
прошивках одинаково (см. `farm/redteam/trace.py`) — при сбое сигнал тихо
уходит в нейтральный 0.5, а не в ошибку.

### Аппаратная аттестация и аккаунт-граф — как подключить по-настоящему

```python
from farm.redteam.harness import run_harness

report = run_harness(
    serials=["79AULJHYVCKRKF5L"],
    attestation_by_serial={"79AULJHYVCKRKF5L": "MEETS_DEVICE_INTEGRITY"},
    account_signals_by_serial={
        "79AULJHYVCKRKF5L": {"accounts_per_device": 1, "actions_per_minute": 6},
    },
)
```

Вердикт Play Integrity и метрики аккаунта харнесс сам получить не может —
это данные вашего приложения и бэкенда. Передавайте их сюда, когда они
появятся; без них соответствующий сигнал остаётся нейтральным (0.5) и
честно об этом пишет в `note`.

## Запуск

```bash
# все онлайн-устройства фермы, по 5 повторов на профиль
python -m farm.redteam.harness --all --repeats 5

# конкретные устройства
python -m farm.redteam.harness --serial 79AULJHYVCKRKF5L --serial emulator-5554
```

Каждый прогон сохраняет `artifacts/redteam/<run_id>/report.json` с полным
списком запусков, скорингом, вкладом сигналов и сводкой по флоту (IP/подсеть,
общая прошивка). В консоль печатается:

- **false negative rate** — доля `bot`-прогонов, которые детектор принял за
  человека;
- **false positive rate** — доля `human`-прогонов, ошибочно помеченных как
  бот;
- confusion matrix по всем четырём комбинациям профиль→вердикт;
- сводка по флоту, если передано больше одного устройства.

## Тесты

`tests/test_redteam.py` — чистая логика на синтетике, устройство не нужно:
`pytest tests/test_redteam.py`.

## Как расширять

- Новый сигнал: `detector.register("имя", вес, fn)`, где `fn(features) ->
  (0..1, пояснение)`. `features` — словарь, который собирает `harness.py`;
  добавляйте туда свои поля по аналогии с уже существующими.
- Другой сценарий: harness всегда гоняет `scenarios/_redteam_probe.py`.
  Замените его код — единственное требование, чтобы жесты шли через
  `ctx.tap` / `ctx.swipe` / `ctx.key` (а не напрямую в `ctx.d`), иначе
  `RecordingContext` их не увидит.
- Более честный «человеческий» профиль: `RecordingContext.humanize` сейчас —
  это просто равномерный шум. Настоящая биометрия жеста — кривые с
  ускорением/замедлением, а не константный сдвиг; именно поэтому наивный
  `random.uniform` — это верхняя граница того, что вообще стоит пытаться
  «спрятать» таким способом, а `gesture_trace` его всё равно не обманет.
